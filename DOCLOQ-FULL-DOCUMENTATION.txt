================================================================================
1. SYSTEM ARCHITECTURE OVERVIEW
================================================================================

DocLoq is a security-first document management system designed for
enterprise/government environments that require maximum data protection.

Architecture Layers:
--------------------

  [Frontend - React 19 + Vite + TailwindCSS]
       |
       | HTTPS + JWT Auth
       v
  [Backend - Express 5 + Node.js]
       |
       +---> [PostgreSQL 16]     Primary database (Drizzle ORM)
       +---> [MinIO]             S3-compatible object storage
       +---> [Vault]             Key management (Transit engine)
       +---> [ClamAV]            Malware scanning
       +---> [Qdrant Cloud]      Vector database (AI semantic search)
       +---> [MongoDB]           AI analysis result cache
       +---> [OpenAI API]        GPT-4.1-mini + text-embedding-3-small
       +---> [OnlyOffice]        Document editing/conversion
       +---> [DocuSeal]          E-signature service
       +---> [Polygon Chain]     Blockchain anchoring (ethers.js)

Multi-Tenant Design:
- Every user belongs to an organization
- All data is scoped by organizationId
- Separate encryption keys per document (envelope encryption)

5. DOCUMENT UPLOAD PIPELINE (15 STEPS)
================================================================================

File: backend/src/services/upload-pipeline.service.js

User Upload via HTTPS (React -> Express)
       |
       v
[1] VALIDATE
    - MIME type whitelist check
    - Magic bytes verification (file-type library)
    - File size <= 50MB
       |
       v
[2] TEMP STORE
    - Buffer saved to /storage/temp/{sessionId}{ext}
    - Record created in temporaryUploads table (status: scanning)
       |
       v
[3] CLAMAV SCAN
    - TCP INSTREAM protocol to ClamAV container :3310
    - 2KB chunked streaming
    - CLEAN -> continue
    - INFECTED -> secureWipe(tempPath) -> reject with threat name
       |
       v
[4] EXTRACT TEXT
    - PDF: pdf-parse library
    - TXT: raw UTF-8
    - Other: skip (no text extraction)
       |
       v
[5] NORMALIZE
    - 7-step normalization:
      1. Lowercase
      2. Collapse whitespace
      3. Strip punctuation
      4. Strip special characters
      5. Unicode NFKD normalization
      6. Strip diacritics
      7. Final trim
       |
       v
[6] DOCUMENT DNA
    - SHA-256 (exact match)
    - SimHash 64-bit (similarity detection)
    - SSDEEP (fuzzy hash)
    - Hash computed from normalizedText (or raw buffer if no text)
       |
       v
[7] DUPLICATE CHECK
    - Query DB for exact SHA-256 match
    - Check SimHash Hamming distance <= 10 (~84% similar)
    - Warning if duplicate found (upload continues)
       |
       v
[8] HONEYTOKEN INJECT (text files only)
    - Method 1: Zero-Width Characters (U+200B/C/D, U+FEFF) at 8 positions
    - Method 2: Homoglyph substitution (Latin->Cyrillic) at 15 positions
    - Method 3: Whitespace encoding (trailing space=0, tab=1) at 20 lines
    - Combined payload hash stored for validation
       |
       v
[9] QR CODE
    - HMAC-SHA256 signed payload
    - QR image generated -> stored in MinIO qr bucket
    - 8-char short code for public verification endpoint
       |
       v
[10] ENCRYPT
     - Generate per-document key via Vault Transit (or local fallback)
     - AES-256-GCM encryption
     - Produces: encryptedBuffer + authTag
     - Plaintext key exists ONLY in memory, encrypted key stored in DB
       |
       v
[11] STORE TO MINIO
     - PutObject to bucket "docloq-documents"
     - Key: {documentId}/{timestamp}{ext}.enc
     - Metadata sidecar: .meta.json (authTag, originalName, mimeType)
       |
       v
[12] DATABASE INSERT
     - Atomic transaction:
       documents + documentVersions + documentHoneytokens +
       documentQrCodes + auditLogs + update temporaryUploads
       |
       v
[13] SECURE WIPE
     - Overwrite temp file with zeros (64KB chunks) -> unlink
     - 3-pass secure deletion
       |
       v
[14] VECTOR INDEX (DEFERRED)
     - Log: "Vector indexing deferred (requires user AI access grant)"
     - Only indexed when user explicitly grants AI access
       |
       v
[15] RETURN RESPONSE
     - { document, version, qrCode, dna, encryption, storage, warnings }

Supported MIME Types:
  - application/pdf
  - application/msword, application/vnd.openxmlformats-officedocument.*
  - application/vnd.ms-excel, application/vnd.ms-powerpoint
  - text/plain, text/csv, text/rtf
  - image/png, image/jpeg
  - application/vnd.oasis.opendocument.*

6. DOCUMENT DOWNLOAD FLOW (WITH PER-DOWNLOAD WATERMARKING)
================================================================================

GET /api/documents/:id/download
       |
       v
Auth check (JWT) + Permission check (owner / team / folder permission)
       |
       v
Query documentVersions -> s3Key, encryptionKeyId, encryptionIv
       |
       v
MinIO GetObject -> encrypted buffer
       |
       v
Read .meta.json sidecar -> authTag
       |
       v
Vault Transit decryptDataKey(encryptedKey) -> plaintextKey
  (or local fallback: decryptDocumentKey)
       |
       v
decryptFile(encryptedBuffer, plaintextKey, iv, authTag) -> plaintext buffer
       |
       v
*** NEW: PER-DOWNLOAD INVISIBLE WATERMARK INJECTION ***
       |
       +---> Generate watermarkId (UUID)
       +---> Build payload: {w: watermarkId, d: docId, u: downloaderId, t: ISO timestamp}
       +---> watermarkBuffer(decryptedBuffer, mimeType, watermarkFn)
       |        |
       |        +---> TXT: direct UTF-8 string injection
       |        +---> DOCX: JSZip → word/document.xml → inject into <w:t> elements
       |        +---> PDF: pdf-lib → drawText(invisible, opacity:0) on page 1
       |        +---> Other: skip watermarking, serve original
       |
       +---> Invisible chars: U+2060, U+2061, U+2062, U+2063
       |     (non-overlapping with upload honeytoken chars U+200B-FEFF)
       |
       +---> Fire-and-forget: INSERT into downloadWatermarks table
       +---> Include watermarkId in audit log
       |
       v
Set Content-Disposition + Content-Type headers -> stream watermarked buffer

Also applies to: GET /api/documents/:id/download-as (converted downloads)
Does NOT apply to: GET /api/documents/:id/file (OnlyOffice serving)

7. AI DOCUMENT ANALYSIS FLOW
================================================================================

--- AI ACCESS GRANT SYSTEM ---

Security concept: Documents are BLOCKED from AI by default.
User must explicitly grant access before AI can process them.

Rationale:
  - Data sovereignty: user controls if content is processed by AI
  - GDPR Art 6 compliance: consent before processing
  - Defense-in-depth: encrypted docs in MinIO not auto-exposed to AI

Flow:

  User Upload Document

  4. Read .meta.json sidecar -> authTag
  5. Decrypt with Vault/local key
  6. Extract text (pdf-parse / raw text)
  7. Generate embedding via OpenAI (text-embedding-3-small)
  8. Upsert to Qdrant Cloud (with organizationId filter)
  9. Update DB: aiAccessGranted = true
  10. Audit log: action = 'ai_grant_access'

--- ANALYZE DOCUMENT FLOW ---

POST /api/ai-analysis/documents/:id/analyze
  1. Sanitize prompt input
  2. Detect prompt injection (15 regex patterns)
  3. Verify aiAccessGranted = true
  4. Check MongoDB cache (key = SHA-256(documentId + normalized_prompt))
     - Cache HIT -> return cached result + record history
  5. If cache MISS:
     a. Decrypt document (download -> decrypt -> extract text)
     b. Truncate to 15,000 chars if needed
     c. Search Qdrant for similar documents (top 3)

     e. Call OpenAI GPT-4.1-mini with structured JSON output
     f. Parse response (summary, keyMetrics, sentiment, charts, etc.)
     g. Cache result in MongoDB (24h TTL)

8. SECURITY FEATURES
================================================================================

8.1 ENCRYPTION
    - Algorithm: AES-256-GCM (authenticated encryption)
    - Pattern: Envelope encryption
      * Master key (Vault Transit or local) encrypts per-document keys
      * Per-document key encrypts file content
      * IV (Initialization Vector) unique per encryption
      * AuthTag stored in .meta.json sidecar
    - Key material never leaves Vault in production

8.2 MALWARE SCANNING
    - ClamAV integration via TCP INSTREAM protocol
    - Scans uploaded files BEFORE encryption
    - 2KB chunked streaming for memory efficiency
    - Infected files: secure-wiped immediately
    - Dev mode: can be disabled (SCANNER_ENABLED=false)

8.3 HONEYTOKENS (Document Leak Detection)
    - Three injection methods (invisible to reader):
      1. Zero-Width Characters: Unicode U+200B/C/D/FEFF at 8 positions
      2. Homoglyph Substitution: Latin->Cyrillic lookalikes at 15 positions
      3. Whitespace Encoding: trailing space/tab on 20 lines
    - Payload: documentId, userId, organizationId, timestamp
    - Combined payload hash for validation
    - Can trace leaked documents back to source user

8.4 QR CODE VERIFICATION
    - HMAC-SHA256 signed payload
    - Contains: documentId, SHA-256 hash, organization, timestamp
    - 8-character random short code for public verification URL
    - Timing-safe signature comparison
    - QR images stored in dedicated MinIO bucket

8.5 DOCUMENT DNA (Hashing)
    - SHA-256: exact match detection
    - SimHash (64-bit): similarity detection (Hamming distance <= 10)
    - SSDEEP: fuzzy hash for near-duplicate detection
    - Applied to normalized text (7-step normalization)

8.6 SECURE DELETION
    - Zero-overwrite in 64KB chunks before unlinking
    - Applied to all temporary files after processing
    - Recursive directory wiping support

8.7 CRYPTO SHREDDING (GDPR Art 17)
    - Delete encryption key from Vault Transit
    - Nullify encryption key reference in database
    - Delete vector embedding from Qdrant
    - Delete ciphertext from storage
    - Mark document as deleted
    - Full audit trail of shredding operation

8.8 AUTHENTICATION & AUTHORIZATION
    - JWT-based session management (3-hour idle timeout)
    - Two-Factor Authentication (TOTP via authenticator app)
    - Email OTP as alternative 2FA method
    - hCaptcha integration (configurable)
    - Role-based access control (6 roles)
    - Custom role system with resource-level permissions
    - Folder permission inheritance to subfolders
    - Admin separate auth system with OTP

8.9 PROMPT INJECTION DETECTION
    - 15 regex patterns for common injection attempts
    - Input sanitization for all AI prompts
    - System prompt protection (never reveal internal instructions)
        
8.10 BLOCKCHAIN ANCHORING (Polygon)
     - Network: Polygon (mainnet chainId 137, Amoy testnet chainId 80002)
     - Smart Contract: DocLoqAnchor.sol (Solidity 0.8.20+)
     - Gas-optimized: all data as bytes32/uint (no string storage)
     - NO PII stored on-chain — only SHA-256 content hashes
     - Organization IDs pseudonymized via keccak256()
     - Packed structs (uint32+uint64+bool fit in 1 storage slot)
     - Batch anchoring via Merkle root (1 transaction for N documents)
     - Events used for historical data (cheaper than storage)
     - Access control: owner + authorized anchors mapping
     - Only admin/owner can manually anchor documents (user consent model)
     - Auto-anchor-on-edit toggle per document
     - Only admin/owner can verify document authenticity from blockchain
     - Backend: ethers.js v6 (JsonRpcProvider + Wallet + Contract)
     - Graceful degradation: BLOCKCHAIN_ENABLED=false until wallet configured

8.11 PER-DOWNLOAD INVISIBLE WATERMARKING (Leak Identification)
     - Purpose: Identify WHICH USER leaked a document (not just the uploader)
     - Separate from honeytokens (8.3): honeytokens identify uploader,
       download watermarks identify the specific downloader
     - Every download event creates a unique watermarked copy
     - Encoding: 4 Unicode invisible characters (U+2060-U+2063)
       * U+2060 Word Joiner
       * U+2061 Function Application
       * U+2062 Invisible Times
       * U+2063 Invisible Separator
     - Non-overlapping with honeytoken chars (U+200B/C/D/FEFF)
     - 2-bit-per-char encoding (same scheme as ZWC honeytokens)
     - Payload: {watermarkId, documentId, downloaderId, timestamp}
     - Randomized injection positions via crypto.randomInt()
       (prevents diff-comparison watermark stripping)
     - 12 injection points distributed across document text
     - Format support: TXT (direct), DOCX (XML modification), PDF (invisible text)
     - Scanner: upload suspected leaked file → extract → decode → DB lookup → identify
     - Dual-layer detection: scans for both download watermarks AND upload honeytokens
     - Records stored in downloadWatermarks table with IP, user agent, payload hash

13. AUTHENTICATION & AUTHORIZATION
================================================================================

--- AUTHENTICATION FLOW ---

1. User submits email + password (+ hCaptcha if enabled)
2. Server verifies credentials
3. If 2FA enabled:
   a. Return { requires2FA: true, userId }
   b. User enters TOTP code (authenticator) or email OTP
   c. Server verifies code
4. JWT token issued (stored in cookie + localStorage)
5. Session created in userSessions table
6. 3-hour idle timeout enforced

--- MIDDLEWARE ---

authenticate         Verify JWT, enforce idle timeout, attach req.user
authorize(roles)     Role-based access (e.g., ['admin', 'super_admin'])
optionalAuth         Allow unauthenticated access, attach user if valid
authenticateAdmin    Verify admin JWT + admin session
requireSuperAdmin    Enforce super_admin role

--- PERMISSION SYSTEM ---

getUserPermissionLevel(userId, resourceType, resourceId, organizationId)
  -> Returns: 'none' | 'viewer' | 'editor' | 'admin'

Permission cascade:
  - Super admin/admin: full access always
  - Custom roles: resource-level permissions
  - Folder permissions: inherit to subfolders + contained documents
  - Document permissions: direct assignment

requireDocumentPermission(minLevel)  Enforce on document routes
requireFolderPermission(minLevel)    Enforce on folder routes

--- ROLES ---

Built-in roles: super_admin, admin, manager, user, auditor, viewer
Custom roles: organization-level, with per-resource permissions

15. INVISIBLE DOWNLOAD WATERMARKING (LEAK IDENTIFICATION)
================================================================================

--- PROBLEM ---

DocLoq already has upload-time honeytokens (Section 8.3) that encode the
UPLOADER's identity into every document. However, when 5 users download the
same document, they all receive identical copies. If a document leaks, the
honeytoken can only identify who uploaded it — not who leaked it.

--- SOLUTION ---

Per-download invisible watermarking injects a UNIQUE watermark into every
downloaded copy, encoding the DOWNLOADER's identity. Each download event
produces a distinctly watermarked file. A scanner tool allows admins to
upload a suspected leaked document and identify the specific leaker.

--- ARCHITECTURE ---

    UPLOAD TIME (existing):              DOWNLOAD TIME (new):
    honeytoken.service.js                download-watermark.service.js
    Chars: U+200B, U+200C, U+200D, FEFF Chars: U+2060, U+2061, U+2062, U+2063
    Payload: {uploader}                  Payload: {downloader, watermarkId}
    Same for all copies                  Unique per download event
    Stored: documentHoneytokens table    Stored: downloadWatermarks table

--- ENCODING SCHEME ---

Characters (2-bit encoding, same approach as ZWC honeytokens):
  00 → U+2060 (Word Joiner)
  01 → U+2061 (Function Application)
  10 → U+2062 (Invisible Times)
  11 → U+2063 (Invisible Separator)

These characters are:
  - Invisible in all document viewers (Word, PDF readers, browsers)
  - Non-overlapping with existing honeytoken characters
  - Preserved through copy-paste operations
  - Part of the Unicode standard (General Punctuation block)

Payload format: JSON → 8 bits per character → 2-bit pairs → invisible chars
  { "w": "watermarkId-uuid", "d": "docId", "u": "userId", "t": "ISO-timestamp" }

--- INJECTION PROCESS ---

1. Generate watermarkId (UUID) for this download event
2. Build payload: {w, d, u, t}
3. Encode payload → bits → invisible character string
4. Split into 12 chunks (configurable positionCount)
5. Generate random insertion positions via crypto.randomInt()
   (truly random — makes diff-comparison stripping impractical)
6. Insert chunks at positions throughout document text
7. Rewrite document buffer with watermarked text:
   - TXT: direct string replacement, re-encode UTF-8
   - DOCX: unzip → modify word/document.xml → inject into first <w:t>
           element with xml:space="preserve" → re-zip
   - PDF: pdf-lib drawText(invisible, x:0, y:0, size:1, opacity:0)
          on first page + embed in PDF keywords metadata
   - XLSX/PPTX: inject via custom XML part in ZIP archive
8. Store watermark record in downloadWatermarks table (fire-and-forget)
9. Include watermarkId in audit log
10. Stream watermarked buffer to user

--- EXTRACTION / SCANNING PROCESS ---

1. Admin uploads suspected leaked document to scanner
2. Extract text from document (same extractText() as upload pipeline)
3. Scan for download watermarks: regex /[\u2060-\u2063]+/g
4. Scan for upload honeytokens: regex /[\u200B\u200C\u200D\uFEFF]+/g
5. Decode invisible chars → bits → JSON → payload
6. Validate payload structure (watermarkId, docId, userId, timestamp)
7. Calculate confidence score (0-1) based on payload completeness
8. DB lookup: watermarkId → downloadWatermarks → JOIN users
9. Return results:
   - Download watermark found: downloader name, email, timestamp, IP, confidence
   - Upload honeytoken found: uploader name, method, confidence
   - Nothing found: "document may have been sanitized or is not from this system"

--- FILES ---

Backend:
  backend/src/services/download-watermark.service.js   Inject/extract watermarks
  backend/src/services/document-rewriter.service.js    Format-specific buffer rewriting
  backend/src/controllers/watermark-scanner.controller.js  Scanner API endpoints
  backend/src/routes/watermark-scanner.routes.js       Route definitions
  backend/src/config/upload.config.js                  downloadWatermark config section
  backend/src/db/schema.js                             downloadWatermarks table

--- CONFIGURATION ---

Environment variables:
  DOWNLOAD_WATERMARK_ENABLED=true|false  (default: true)

Config (upload.config.js → downloadWatermark):
  enabled: true                          Toggle watermarking on/off
  chars: [U+2060, U+2061, U+2062, U+2063]  Invisible encoding characters
  positionCount: 12                      Number of injection points
  supportedCategories: [pdf, office, text]  File types to watermark

--- ANTI-STRIPPING MEASURES ---

1. Randomized positions: Each download uses crypto.randomInt() for positions,
   so comparing two copies doesn't reveal a consistent pattern to strip.
2. Dual layer: Upload honeytokens (3 methods) survive independently of
   download watermarks — stripping one layer still leaves the other.
3. Multiple injection points (12 by default): Partial text extraction or
   truncation still captures enough watermark fragments to decode.
4. Different encoding per format: PDF uses text annotation + metadata,
   DOCX uses XML text nodes — format conversion may preserve at least one.

--- PERFORMANCE ---

Estimated overhead per download:
  - Text extraction: ~100ms
  - Watermark injection: ~5ms
  - DOCX re-zip: ~100ms / PDF modification: ~150ms
  - DB insert (fire-and-forget): ~10ms
  Total: ~200-350ms (within 500ms budget)

16. BLOCKCHAIN DOCUMENT ANCHORING (POLYGON)
================================================================================

Purpose: Provide immutable proof of document authenticity and integrity
by anchoring document hashes to the Polygon blockchain.

--- SMART CONTRACT ---

File: backend/contracts/DocLoqAnchor.sol
ABI:  backend/contracts/DocLoqAnchor.json

Contract: DocLoqAnchor (Solidity 0.8.20+)

Storage (gas-optimized — all bytes32/uint, no strings):
  - mapping(bytes32 => DocumentAnchor) anchors
    * documentHash (bytes32)    SHA-256 hash of document content
    * pseudoOrgId  (bytes32)    keccak256 of organization UUID
    * versionNumber (uint32)    Document version at time of anchoring
    * timestamp     (uint64)    Block timestamp
    * exists        (bool)      Existence flag
  - mapping(bytes32 => MerkleAnchor) merkleAnchors
    * merkleRoot    (bytes32)   Root hash of batch
    * documentCount (uint32)    Number of documents in batch
    * timestamp     (uint64)    Block timestamp
    * exists        (bool)      Existence flag

Access Control:
  - owner: deployer address
  - mapping(address => bool) authorizedAnchors
  - onlyOwner: for authorize/revoke functions
  - onlyAuthorized: for anchoring operations

Functions:
  authorizeAnchor(address)    Owner adds backend wallet as authorized
  revokeAnchor(address)       Owner removes authorization
  anchorDocument(bytes32 anchorId, bytes32 docHash, bytes32 pseudoOrgId, uint32 version)
  updateAnchor(bytes32 anchorId, bytes32 newHash, uint32 newVersion)
  anchorBatch(bytes32 merkleRoot, uint32 docCount)
  verifyDocument(bytes32 anchorId, bytes32 docHash) view → (bool, uint64)
  verifyBatch(bytes32 merkleRoot) view → (bool, uint64, uint32)
  getAnchor(bytes32 anchorId) view → full anchor data
  transferOwnership(address newOwner)

Events:
  DocumentAnchored(bytes32 indexed anchorId, bytes32 docHash, uint64 timestamp)
  AnchorUpdated(bytes32 indexed anchorId, bytes32 newHash, uint32 newVersion)
  BatchAnchored(bytes32 indexed merkleRoot, uint32 docCount, uint64 timestamp)
  AnchorAuthorized(address indexed account)
  AnchorRevoked(address indexed account)
  OwnershipTransferred(address indexed prev, address indexed next)

Gas Optimizations:
  1. All data stored as bytes32/uint (no string storage)
  2. Packed struct: uint32 + uint64 + bool fit in single 32-byte slot
  3. Batch anchoring via Merkle root (1 tx for N documents)
  4. Events for historical data (cheaper than on-chain storage)
  5. View functions for verification (zero gas cost)

Data Protection (GDPR/Privacy):
  - NO PII stored on-chain (no names, emails, filenames)
  - Organization IDs pseudonymized: keccak256(orgUUID)
  - Only document content hashes stored (SHA-256, irreversible)
  - All identifiable data stays in PostgreSQL
  - Document-to-anchor mapping only in off-chain database

--- ANCHORING FLOW ---

  1. Admin clicks "Anchor to Polygon" on document detail modal
  2. Backend validates: document exists, has contentHash, user has admin role
  3. Generate anchorId = keccak256(documentId)
  4. Pseudonymize orgId = keccak256(organizationId)
  5. Call contract.anchorDocument(anchorId, hash, pseudoOrgId, version)
  6. Wait for transaction confirmation (configurable, default 1)
  7. Insert record into blockchainAnchors table
  8. Update documents.blockchainAnchored = true
  9. Return { txHash, blockNumber, gasUsed } to frontend

--- VERIFICATION FLOW ---

  1. Admin clicks "Verify Integrity" on anchored document
  2. Backend generates anchorId from documentId
  3. Call contract.verifyDocument(anchorId, currentContentHash) — view (no gas)
  4. Return { verified: bool, onChainHash, timestamp }
  5. Frontend shows green (match) or amber (mismatch) result

--- AUTO-ANCHOR ON EDIT ---

  1. Admin toggles "Auto-anchor on edit" switch in document modal
  2. Sets documents.autoAnchorOnEdit = true in database
  3. When document is saved via OnlyOffice callback:
     a. Upload pipeline processes new content
     b. If autoAnchorOnEdit=true AND BLOCKCHAIN_ENABLED=true:
        - Fire-and-forget call to blockchain.updateAnchor()
        - Re-anchors with new content hash and version number
  4. Keeps on-chain record synchronized with document edits

--- BATCH ANCHORING ---

  1. Admin selects multiple documents and uses "Batch Anchor"
  2. Backend builds Merkle tree from document content hashes
  3. Single transaction: contract.anchorBatch(merkleRoot, docCount)
  4. Individual Merkle proofs stored per document in blockchainAnchors
  5. Verification: reconstruct proof path to verify leaf against root
  6. Massive gas savings: 1 tx for 100+ documents

Environment Variables:
  POLYGON_RPC_URL=https://polygon-rpc.com    (or Amoy testnet RPC)
  POLYGON_PRIVATE_KEY=                        (wallet private key)
  POLYGON_CONTRACT_ADDRESS=                   (deployed contract address)
  POLYGON_CHAIN_ID=137                        (137=mainnet, 80002=Amoy)
  BLOCKCHAIN_ENABLED=false                    (default off until configured)

Config: backend/src/config/upload.config.js → blockchain section
  enabled, rpcUrl, chainId, privateKey, contractAddress
  confirmations (default 1), gasLimits: { anchor: 100000, batch: 500000 }
